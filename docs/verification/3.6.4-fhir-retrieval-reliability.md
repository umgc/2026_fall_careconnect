## 1. How it was tested

`FHIRServiceReliabilityVerificationTest` starts a local HTTP server that stands in for the Blue
Button FHIR API and drives the real HAPI FHIR client through `FHIRService`, so every request,
header, query and pagination link is real. No network access or CMS credentials are needed, so it
runs in CI.

To make that possible, `FHIRService` gained a package-private constructor that takes the base URL.
The public no-argument constructor still uses the CMS sandbox, so production behaviour is unchanged.

```bash
cd backend/core
./mvnw -B test -Dtest=FHIRServiceReliabilityVerificationTest
```

Environment: Windows 11, OpenJDK 17.0.20, Maven wrapper, 2026-09-29.

## 3. Findings

| Defect | Finding | Evidence | Suggested fix | Owner |
|---|---|---|---|---|
| DEF-MCR-01 | **Partial failure loses data.** If a later page fails, the exception propagates and the records from earlier pages are discarded; nothing is stored and the caller cannot tell how far retrieval got. | TC-MCR-FHIR-008, 014 | Return a result that carries the records retrieved so far plus the failure (or persist per page), as WBS 6.2.35 requires. | Max (3.1.1) / Shayne (3.1.4) |
| DEF-MCR-02 | **No retry or backoff.** HTTP 429 (rate limited) and 503 fail on the first attempt. FR-MCR-23 requires up to 3 attempts with exponential backoff from 2 seconds on Medicare rate limiting. | TC-MCR-FHIR-009; 013 must still pass after the fix | Retry 429/5xx with exponential backoff and a cap, honour `Retry-After`; never retry 4xx other than 429. | Max / Shayne |
| DEF-MCR-03 | **Records dropped when `Bundle.total` is absent.** `total` is optional (0..1) in FHIR search bundles. The Coverage and EOB paths check `getTotal() == 0` before reading entries, so a page that omits `total` returns nothing even though it has records. The Patient lookup checks `getTotal() == 1`, so a bundle holding one Patient but no `total` is refused. | TC-MCR-FHIR-010, 011, 012 | Decide emptiness from the entries (`hasEntry()`), and count Patient entries, not `getTotal()`. | Max |
| DEF-MCR-04 | **Minor:** the Coverage path's error message says "Invalid EOB response type", which is misleading when diagnosing a Coverage failure. | Code review | Change the message to "Invalid Coverage response type". | Max |

When DEF-MCR-01 to 03 are fixed, flip the matching cases (TC-MCR-FHIR-008 to 012 and 014) to assert
the requirement instead of the current behaviour.
