## 1. How it was tested

`FHIRServiceReliabilityVerificationTest` starts a local HTTP server that stands in for the Blue
Button FHIR API and drives the real HAPI FHIR client through `FHIRService`, so every request,
header, query and pagination link is real. No network access or CMS credentials are needed, so it
runs in CI.

To make that possible, `FHIRService` gained a package-private constructor that takes the base URL.
The public no-argument constructor still uses the CMS sandbox, so production behaviour is unchanged.
A second package-private constructor also replaces the wait between retries, so the retry cases
record the waits instead of sleeping. The `/results` cases (029…031) call `BluebuttonController`
with the real `FHIRService` over the same stand-in and a mocked OAuth2 sign-in.

```bash
cd backend/core
./mvnw -B test -Dtest=FHIRServiceReliabilityVerificationTest
```

Environment: Windows 11, OpenJDK 17.0.20, Maven wrapper, 2026-09-29.

## 3. Findings

| DEF-MCR-01 | **Fix in PR #223** (2026-10-01), verified 2026-10-02; closes on merge: `retrieveMedicareCoverage` / `retrieveMedicareEOB` return a `BlueButtonRetrieval` with the records so far, the failed page and its status; `/results` reports `complete` and what is missing. Original finding: **Partial failure loses data.** If a later page fails, the exception propagates and the records from earlier pages are discarded; nothing is stored and the caller cannot tell how far retrieval got. | TC-MCR-FHIR-008, 014 | Return a result that carries the records retrieved so far plus the failure (or persist per page), as WBS 6.2.35 requires. | Max (3.1.1) / Shayne (3.1.4) |
| DEF-MCR-02 | **Fix in PR #223** (2026-10-01), verified 2026-10-02; closes on merge: `BlueButtonRetryPolicy` retries 429/5xx up to 3 attempts (2 s, 4 s), honours `Retry-After` up to 30 s, never retries other 4xx. Original finding: **No retry or backoff.** HTTP 429 (rate limited) and 503 fail on the first attempt. FR-MCR-23 requires up to 3 attempts with exponential backoff from 2 seconds on Medicare rate limiting. | TC-MCR-FHIR-009; 013 must still pass after the fix | Retry 429/5xx with exponential backoff and a cap, honour `Retry-After`; never retry 4xx other than 429. | Max / Shayne |
| DEF-MCR-03 | **Fixed 2026-10-02** in the PR #223 review (the PR #208 suggested fix, rebased and applied by the Testing Lead, commit `4d8cc735`), re-run by Rich Galero 2026-10-03; closes on merge: `paged()` decides emptiness with `hasEntry()` and the Patient lookup counts entries. Original finding: **Records dropped when `Bundle.total` is absent.** `total` is optional (0..1) in FHIR search bundles. The Coverage and EOB paths check `getTotal() == 0` before reading entries, so a page that omits `total` returns nothing even though it has records. The Patient lookup checks `getTotal() == 1`, so a bundle holding one Patient but no `total` is refused. | TC-MCR-FHIR-010, 011, 012 | Decide emptiness from the entries (`hasEntry()`), and count Patient entries, not `getTotal()`. The PR #208 patch no longer applies after PR #223 and is withdrawn. | Fixed by the Testing Lead in Max's code; re-run by Rich Galero |
| DEF-MCR-04 | **Fixed 2026-10-02** with DEF-MCR-03, re-run by Rich Galero 2026-10-03; closes on merge: the message names the resource searched for, and TC-MCR-FHIR-007 asserts it. Original finding: **Minor:** the Coverage path's error message says "Invalid EOB response type", which is misleading when diagnosing a Coverage failure. | TC-MCR-FHIR-007 | Change the message to "Invalid Coverage response type" (in PR #223's shared code, name the resource searched for). | Fixed by the Testing Lead in Max's code; re-run by Rich Galero |
| DEF-MCR-05 | **Raised and fixed 2026-10-02** in the PR #223 review (commit `4d8cc735`), re-run by Rich Galero 2026-10-03; closes on merge: a 401 on a later page was returned as a partial result, so `/results` went on to request ExplanationOfBenefit with the token Medicare had just rejected.
