## 1. What is in place

- `frontend/integration_test/team_e_m3/flows.dart` lists the five flows: case ID, work package,
  SRS trace, dependencies, steps and pass criteria. It also holds `skipReasonFor`, the skip rule.
- `frontend/integration_test/team_e_m3_workflows_e2e_test.dart` runs one test per flow.
  - It is **opt-in** (`--dart-define=TEAM_E_M3_E2E=true`), so other teams' emulator jobs never run it
    by accident. Team E CI does not run `integration_test/` today.
  - A flow whose features have not merged is **skipped**, and the skip reason names the missing
    package.
  - A flow marked `landed` whose steps are not wired yet **fails** with its step list, so it can't
    pass by accident.
- `frontend/test/integration_test_support/team_e_m3_flows_test.dart` (TC-E2E-005…009) checks the
  flow catalog and the skip rule. It sits under `test/`, so the develop merge CI (`develop-merge-ci.yml`,
  the full `test/` suite) runs it. The Feature Branch CI on pull requests to `team-e-develop` selected no
  test file on this PR (2026-10-01), so a green check there does not show the guard cases ran. No CI
  job runs `integration_test/`.

## 4. Wiring a flow when its feature lands

1. Confirm the feature is merged to `team-e-develop` and its unit tests ran and passed (entry
   criterion). The evidence must name the tests: a CI log that lists them, or a local run. A green
   Feature Branch CI check alone is not enough, because it can pass without running any test.
2. Add the flow's steps to `_wiredFlows` in the test file, using the feature's real screens and
   endpoints.
3. Set `landed: true` for the flow in `flows.dart`.
4. Run the suite on the Android emulator (and web for TC-E2E-001), then record the result in the
   M3 test report and the RTM.
5. Any failure gets an issue with an owner (exit criterion).
