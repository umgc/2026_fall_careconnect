## 1. What was verified

The shared contract suite (`AbstractIdentityReconciliationContractTest`, 16 scenarios, run through
`InMemoryContractTest`) already covers each rule in the README one at a time. This package adds
`ReconciliationVerificationTest` (12 tests) for the cases that suite does not exercise: several fields
in one snapshot, repeated syncs, sources arriving out of order, patient isolation, null values, the
`date_of_birth` tie rule, confirming twice, and what happens after a patient declines.

| ID | What it checks | README rule | Result |
|---|---|---|---|
| VER-REC-01 | One snapshot with several fields decides each field independently (accept, agree, fill, skip blank) | Algorithm steps 3–5 | Pass |
| VER-REC-02 | A pending `date_of_birth` does not hold back other fields in the same snapshot | DOB carve-out | Pass |
| VER-REC-03 | The same newer snapshot received twice changes the patient once and writes one audit row | Agree branch, A2 | Pass |
| VER-REC-04 | Three sources arriving out of timestamp order converge on the newest; the loser is still audited | Recency wins, audit on reject | Pass |
| VER-REC-05 | Reconciling one patient never changes another patient's value or baseline | Provenance per (patient, field) | Pass |
| VER-REC-06 | A `null` field value is skipped like a blank one and never erases a real value | Blank/null skip | Pass |
| VER-REC-07 | A `date_of_birth` candidate with exactly the baseline timestamp is rejected, not held pending | A2 applied to DOB | Pass |
| VER-REC-08 | Confirming a `date_of_birth` twice fails the second time and audits once | `finalizePendingDateOfBirth` | Pass |
| VER-REC-09 | After an accepted `date_of_birth`, a sync with the same value does not reopen it | Agree branch after accept | Pass |
| VER-REC-10 | After a patient declines, a newer candidate prompts them again (see Q3) | A3, provenance on decline | Pass (documents current behaviour) |
| VER-REC-11 | Values differing only in letter case count as a disagreement (see Q1) | Not specified | Pass (finding) |
| VER-REC-12 | Surrounding whitespace is kept and counts as a disagreement (see Q2) | Not specified | Pass (finding) |

**Totals:** `ReconciliationVerificationTest` 12/12 pass; `InMemoryContractTest` 16/16 pass (28/28).

### Run it

```bash
cd backend/core
./mvnw -B test -Dtest='ReconciliationVerificationTest,InMemoryContractTest'
```

Environment: Windows 11, OpenJDK 17.0.20, Maven wrapper from `backend/core`, run 2026-09-28.

### Do the tests actually catch defects?

The tie rule was deliberately broken (`isAfter` changed to `!isBefore` in
`RecencyWinsIdentityReconciler`) and the suite re-run. VER-REC-07 failed with
*"Assumption A2 (ties keep the existing value) must apply to date_of_birth too ==> expected
REJECTED_STALE but was PENDING_PATIENT_CONFIRMATION"*. The change was then reverted. A passing run
therefore means the rule holds, not just that the tests are too weak to notice.

## 2. Findings and open questions

None of these are bugs against the README; they are behaviours the README does not decide. Each is
pinned by a test so a change is deliberate.

| # | Question | Current behaviour | Suggested owner |
|---|---|---|---|
| Q1 | Should `Smith` and `SMITH` count as the same value? | Treated as a disagreement: the newer casing overwrites the patient's and an ACCEPTED audit row is written (VER-REC-11). | Requirements (Quinton) with Rich |
| Q2 | Should values be trimmed before comparison? | ` Smith ` is stored with its spaces and beats `Smith` (VER-REC-12). Adapters should probably trim before calling `reconcile()`, or the library should. | Adapter teams / Rich |
| Q3 | After a patient declines a `date_of_birth` change, should the same source be allowed to ask again? | Yes — declining leaves provenance at the old timestamp, so the next newer sync of the same value opens a new PENDING prompt (VER-REC-10). Product may want a declined value to stay declined. | Product owner, recorded as a new assumption (A4) in the README if kept |

## 3. Not yet verifiable (blocked on predecessors)

- **3.2.2 Duplicate and conflict handling** and **3.2.3 User review workflow** : no branch or merged code for
  either was found on the remote (checked 2026-09-28). Their verification will be added to
  this package once they exist, including the medication rule in the README: medication conflicts
  (FR-EHR-07) must be flagged for caregiver review and never auto-resolved by this library.
- **Real-database verification.** Everything above runs against the in-memory fakes. When an adapter
  wires the four interfaces to PostgreSQL, its `AbstractIdentityReconciliationContractTest` subclass
  must also re-run the adversarial check from `ehr-identity-reconciliation/manual-verify/` with the row
  lock stubbed out, as the README requires, to prove the concurrency tests exercise the real lock.
- **Org scoping.** `ehr_identity_field_provenance.sql` still marks the org column TODO; tenant isolation
  across organisations cannot be verified until that column is confirmed.
