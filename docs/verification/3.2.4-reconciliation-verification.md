## 1. What was verified

The shared contract suite (`AbstractIdentityReconciliationContractTest`, 16 scenarios, run through
`InMemoryContractTest`) already covers each rule in the README one at a time. This package adds
`ReconciliationVerificationTest` for the cases that suite does not exercise: several fields
in one snapshot, repeated syncs, sources arriving out of order, patient isolation, null values, the
`date_of_birth` tie rule, confirming twice, what happens after a patient declines, invalid snapshots,
and accepting after a supersede.

Test IDs follow the Test Plan (§3.10, family `TC-EHR-REC`). The contract suite's 16 scenarios are
TC-EHR-REC-013…028.

### Do the tests actually catch defects?

The tie rule was deliberately broken (`isAfter` changed to `!isBefore` in
`RecencyWinsIdentityReconciler`) and the suite re-run. TC-EHR-REC-007 failed with
*"Assumption A2 (ties keep the existing value) must apply to date_of_birth too ==> expected
REJECTED_STALE but was PENDING_PATIENT_CONFIRMATION"*, and the contract suite's tie case
(TC-EHR-REC-018) failed for an ordinary field. The change was then reverted. A passing run
therefore means the rule holds, not just that the tests are too weak to notice.

## 2. Findings and open questions

Q1–Q3 are not bugs against the README; they are behaviours the README does not decide. Each is
pinned by a test so a change is deliberate.

| # | Question | Current behaviour | Suggested owner |
|---|---|---|---|
| Q1 | Should `Smith` and `SMITH` count as the same value? | Treated as a disagreement: the newer casing overwrites the patient's and an ACCEPTED audit row is written (TC-EHR-REC-011). | Requirements (Quinton) with Rich |
| Q2 | Should values be trimmed before comparison? | ` Smith ` is stored with its spaces and beats `Smith` (TC-EHR-REC-012). Adapters should probably trim before calling `reconcile()`, or the library should. | Adapter teams / Rich |
| Q3 | After a patient declines a `date_of_birth` change, should the same source be allowed to ask again? | **Resolved 2026-10-02.** No for the same value: a value the patient declined is discarded on later syncs (REJECTED / SYSTEM, decision `REJECTED_PREVIOUSLY_DECLINED`), so the prompt is not reopened every sync; a genuinely different value still prompts. Raised in the #209 review; Rich suggested resolving it via #206. Covered by TC-EHR-REC-032 (contract suite, in-memory and PostgreSQL). | Done |

**DEF-EHR-REC-01 (defect, found 2026-09-29).** `SourceIdentitySnapshot` accepted null components.
An undated snapshot filled an empty field and stored provenance with a null timestamp; the next newer
disagreement for that field applied its value, wrote an ACCEPTED audit row, and then threw a
`NullPointerException` in `refreshProvenanceIfNewer`. Fixed by requiring all four components in the
record's constructor; verified by TC-EHR-REC-029 and 030. The fix and the two cases are by the same
person, so they need an independent re-run before the defect is closed.

## 3. Not yet verifiable (blocked on predecessors)

- **3.2.2 Duplicate and conflict handling** and **3.2.3 User review workflow** : no branch or merged code for
  either was found on the remote (checked 2026-09-28). Their verification will be added to
  this package once they exist, including the medication rule in the README: medication conflicts
  (FR-EHR-07) must be flagged for caregiver review and never auto-resolved by this library.
- **Real-database verification.** Everything above runs against the in-memory fakes. When an adapter
  wires the four interfaces to PostgreSQL, its `AbstractIdentityReconciliationContractTest` subclass
  must also re-run the adversarial check from `ehr-identity-reconciliation/manual-verify/` with the row
  lock stubbed out, as the README requires, to prove the concurrency tests exercise the real lock.
  The same subclass is where "a failure partway through a snapshot keeps the fields already
  committed" (`IdentityReconciler.reconcile`) can be verified; the in-memory runner has no rollback.
- **Org scoping.** `ece73995` removed `orgId` from the library and its DDL, because no organization or
  tenant identifier exists anywhere in the schema. SRS 1.4 FR-EHR-10 and FR-MCR-18 still require
  organization-identifier multi-tenant isolation. Until the Requirements Owner settles that conflict,
  organization-level isolation cannot be verified; patient-level isolation is TC-EHR-REC-005.
